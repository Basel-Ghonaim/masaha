## Tokens and cookies

| Item | Rule |
|---|---|
| Access token | JWT, HS256 set explicitly on sign and verify, 15 min. Claims: `sub` (the user's id), `mustChangePassword` ([Passwords](#passwords)), `sessionVersion` and `sid`, its session's id (its family's); no role, which the guard reads from the account ([Authorization](#authorization)). Returned in the body, kept in memory by the client. A token without `sessionVersion` or `sid`, signed before it existed, is refused, and the web's refresh replaces it |
| Session version | A number on the account that grows by one each time every session of the account ends (Revocation, below), in the same transaction, under the same session lock, as the deletion of its refresh tokens. Every access token carries the version it was signed under, and `requireAuth` refuses one whose version is no longer the account's ([Authorization](#authorization)): no access token outlives the end of its session, and one signed before a suspension stays refused once the account is restored. The device that changed its password gets a token under the new version |
| Secret | ≥ 32 characters, validated at startup |
| Refresh token | Random opaque value (256 bits), stored as its SHA-256 hash, 7 days, rotated on each refresh in a transaction |
| Session | The tokens rotated from one sign-in form a **family**, named by the id of its first token. Logout ends the whole family, the device's session. **A session lives at most 30 days from its sign-in,** however often it refreshes: every token of the family carries that deadline, set at sign-in and copied on each rotation, and a refresh past it is refused as any ended session is, deleting the family, whatever the presented token's own expiry. The person then signs in again. A password change opens a new session, with its own 30 days |
| Idle (reception) | A session of an account that holds an active `RECEPTION` link, no active `OWNER` link, and is not the admin, as the links read on the request say (a soft-deleted space's links count, as for `OWNER`), **ends after 15 minutes with no request** (`RECEPTION_IDLE_MINUTES`). Its family carries its last use, set at sign-in, copied on each rotation, and renewed by `requireAuth` on each of its requests, written at most once a minute; a passive route renews nothing — today only the desk's polled state, `GET /manage/spaces/:spaceId/occupancy`, so a desk left open with no one at it ends. Past 15 minutes a request answers 401 `SESSION_IDLE` and keeps the family; the refresh that follows deletes it, clears the cookies and answers 401 `SESSION_IDLE`, so the web can say why. Only this device's session ends: the session version is not raised, and the person's other devices stay. An owner, the admin and a plain user are never idle-ended. 2026-10-25, #118 |
| Rotation grace | A token rotated less than 30 s ago is still honoured: its refresh gets a new token of the same family, so two tabs refreshing together, or a refresh retried after a lost answer, stay signed in |
| Reuse | A token rotated **more** than 30 s ago means a copy of it is in use: its family is deleted and the refresh answers 401. The user's other sessions, on other devices, are untouched, so a reception desk on another device keeps working. This cuts a stolen chain once either holder presents a token rotated more than 30 s ago. It does not hold inside the grace: a copy presented within 30 s of a rotation gets its own successor, and from then on thief and owner each rotate their own branch, which reuse detection never sees, until a logout, a password change or a reset ends the session ([finding 21](../architecture/findings/21-a-token-replayed-within-the-grace-window-starts-its-own-branch.md)) |
| Refresh cookie | `masaha_refresh` · `HttpOnly` · `Secure` everywhere but development (a missing `NODE_ENV` refuses to start, never falls back to development) · `SameSite=Strict` · `Path=/api/v1/auth` · 7 days; set and cleared from one shared options object |
| Session hint | `masaha_session=1`, readable by JS, `Path=/`, no secret |
| Recovery cookie | `masaha_reset` · the key of a password recovery ([Passwords](#passwords)), random (256 bits), stored as its SHA-256 hash · `HttpOnly` · `Secure` everywhere but development · `SameSite=Strict` · `Path=/api/v1/auth/password` · lives as long as the recovery, which lives as long as its reset link; set and cleared from one shared options object |
| Cross-site requests | Refresh and logout act on the cookie alone, so they refuse with 403, before touching any cookie, a request the browser marks cross-site (`Sec-Fetch-Site`) or whose `Origin` is not the web's. SameSite=Strict already keeps the cookie off such a request; this stops its answer from clearing the cookies, which would sign the user out. The password routes that read or set the recovery cookie refuse such a request the same way |
| Revocation | Password change, password reset, role change, suspension, the admin's temporary password, a Google link and the deactivation of a reception link end every session of the user: they delete all the user's refresh tokens and raise the session version, so every access token already signed is refused too. Logout ends only its own session and raises nothing: its own access token stays valid until it expires, at most 15 minutes, and the web drops it; a suspension and a temporary password also end every pending reset link. A password change then opens a new session for its own device. A role change includes the `OWNER` role following the links ([ADR 0009](../architecture/decisions/0009-space-scoped-reception-role.md)): a person's first owner link and the end of their last one. An owner link made or ended that leaves the role as it is ends no session: the links loader reads the links on every request, so the access to that space changes at once |

## Sign-in methods

- **Email and password.** There is no phone login.
- **Google**, as an extra option beside the password. The client sends a Google OpenID Connect ID token, and the server verifies it with `jose` against Google's published keys: signature, issuer, audience (Masaha's client ID), expiry and `email_verified`. Scopes are `openid email profile`.
  - A first Google sign-in with an unknown email creates a `USER`.
  - A Google sign-in whose verified email matches an existing account links Google to it automatically **only where Google is the authority for the address**: a `@gmail.com` address, or one in the Google Workspace domain the token's `hd` claim names. Elsewhere, Google's `email_verified` does not prove who holds the address today: a Google account may belong to its former holder (a shared mailbox, an ex-employee).
    - **Never while a temporary password is pending** (`GOOGLE_LINK_NOT_ALLOWED`, [Passwords](#passwords)), checked again under the session lock.
    - **Where it links,** it does so in one transaction under the session lock: Google is linked only if none is yet, the account's password is removed (its forced change with it), and every session of the account ends. Registration proves no inbox, so a password set before the link may be an attacker's who registered the address first (a pre-account takeover); only Google proved the address, so only Google opens the account. The person sets a password again through the reset email. The answer says `linked: true`.
    - **Where it does not,** the sign-in is refused with `GOOGLE_LINK_NOT_ALLOWED`. The person signs in with the password, or resets it.
    - An account already linked to **another** Google account is never relinked: the sign-in is refused with `GOOGLE_TOKEN_INVALID`.
  - A Google-only account has no password, so a password sign-in fails with `INVALID_CREDENTIALS`. It may add a password later.
- Both methods issue the same session ([ADR 0003](../architecture/decisions/0003-session-model.md)).
- **Registering an email that has an account answers `EMAIL_TAKEN`.** That tells the caller the account exists, unlike the forgotten password's answer. It is an accepted trade-off, for usability: a person who already has an account learns to sign in instead. The sign-in limits count each refused registration as a failure.

## Passwords

- bcrypt, cost 12, hashed outside database transactions, by the `users` module ([ADR 0013](../architecture/decisions/0013-identity-modules.md)): a sign-in compares the password first, then re-reads the hash under the session lock and opens the session only if it is still the one that matched. A sign-in for an unknown email, or for an account with no password, still spends one comparison, so its timing does not reveal which accounts exist.
- Policy: at least 8 characters and at most 72 bytes in UTF-8 (bcrypt ignores every byte after the 72nd, and an Arabic letter takes two), with at least one letter and one digit.
- The hash is excluded in the Prisma `select`, never only by the mapper.
- Wrong credentials: generic `INVALID_CREDENTIALS`.
- **Accounts created by someone else** get a temporary password, shown once to hand over, and `mustChangePassword = true`. This covers:
  - an owner account created by the admin;
  - a reception account the owner creates; an email that already has an account is refused, never linked ([ADR 0009](../architecture/decisions/0009-space-scoped-reception-role.md), revised);
  - an admin recovery (below).

  **A temporary password** is 12 characters drawn with Node's `crypto` from an alphabet without look-alikes (no `0`, `O`, `o`, `1`, `l` or `I`), drawn again until it meets the policy. It is answered once, in the answer that creates the account or issues it, under `Cache-Control: no-store`, and never again: no log line, audit entry or error holds it, and the logger redacts a `temporaryPassword` field as it does a password. How it was handed over (WhatsApp, in person, other) is recorded in the audit after it is shown ([the contract](../api/api-contract.md#users-the-admin)).

  **A temporary password expires 7 days after it is issued** (the account stores when; a database `CHECK` keeps that time set while one is pending, and only then). A password sign-in with an expired one is refused with `TEMPORARY_PASSWORD_EXPIRED`, only once the password matches, so only its holder learns it expired. A session opened before the expiry keeps its forced change, and a Google sign-in of an account already linked to Google opens as before: each proved the person before. A new one is issued by whoever created the account (below).

  **While a temporary password is pending, the account has no recovery by email and no Google link.** The email was typed by someone else, and may be wrong: only the person holding the temporary password has proved anything, so a mailbox (or a Google account) at a mistyped address must not open the account. The forgotten password sends nothing, answering as for any address; a link sent before the temporary password was issued is refused at its check and at the reset; a Google sign-in is refused with `GOOGLE_LINK_NOT_ALLOWED`. Once the person changes the temporary password, both work again. **Nor does the account gain any power while one is pending:** the admin neither makes it a space's owner (an upgrade or a link) nor an admin (`ACCOUNT_PASSWORD_PENDING`), checked under the account's lock, because whoever created the account knows that password: a receptionist's owner would hold the new power too. **The forced change confirms or corrects the address** (`POST /me/password { email? }`): a correction is audited, an address another account holds is refused with nothing changed, and each refusal counts under the change's failures limit, so probing addresses through it is bounded as at registration.

  Every endpoint behind `requireAuth` except `/me/password` answers `PASSWORD_CHANGE_REQUIRED` until the password is changed. The access token carries `mustChangePassword`, and `requireAuth` refuses it unless the route allows a pending change. A token whose claim says no change is pending while the account says one is was signed before a temporary password, whose issue ended every session: `requireAuth` answers it 401, on every route, `/me/password` included, so the web's refresh ends that session. The public routes, and those that act on a cookie alone (refresh, logout, the password recovery), never read the claim, so the session's refresh still works, and the web can restore the session and show the change.
- **Changing the password** (`/me/password`) asks for the current one, except during the forced change. The change counts as forced only when **both** the access token's claim and the account say a change is pending, so neither a stale token nor a flag set after the token was issued skips the check.
  - A wrong current password counts under a per-user failures limit ([Rate limits](#rate-limits-fixed-window)): a stolen 15-minute access token must not become unlimited guesses.
  - An account without a password (Google only) sets its first one through the reset email, which proves the inbox, never here: a stolen access token alone must not give a lasting password. It answers `PASSWORD_NOT_SET`.
  - It writes only if the account still has the password and the pending flag it checked (a compare-and-set, so it never overwrites a reset that landed meanwhile), ends every session of the user and any pending reset link, then opens a new session for the device that changed it: a new access token without `mustChangePassword`, and a new refresh cookie.
- **Password reset** is a link sent by email, following the OWASP Forgot Password Cheat Sheet. It is a transactional email, not a notification ([overview › Not in v1](../project/overview.md#not-in-v1)).
  - **The token** is random (256 bits) and stored only as its SHA-256 hash. It is valid for 1 hour, and used once, by one atomic statement, so two concurrent resets cannot both succeed. A delivered link ends the earlier one: one live link per account. A link that is not sent (a cap, the relay) is withdrawn, so the one already in the inbox stays live.
  - **The request** opens a **recovery** in the browser ([ADR 0017](../architecture/decisions/0017-recovery-session.md)), ending the one it held. Its answer and its cookie are the same whether or not the email has an account ([the flow](../features/auth.md#behaviour-and-flows)). An unknown or suspended account, or one whose temporary password is pending, gets no email, and a failed send is only logged. **An answer that sends no email waits about as long as a real send takes,** whatever the reason (no account, a suspended one, a cap, a failed send), so a probe on a fast network cannot tell an address with an account from one without. The wait is drawn anew for each answer, uniformly between 1.5 and 3 seconds, since a fixed delay would itself tell; another link asked for through the recovery waits the same way. The bounds are an estimate of a send through Gmail's SMTP relay (about seven round trips and Google's processing), not a measurement: no send has been timed yet ([finding 65](../architecture/findings/65-the-forgotten-passwords-wait-is-an-estimate-not-a-measurement.md)). **Accepted residual:** a relay slower than the bounds still answers later than any answer that sent nothing, so its outliers stay distinguishable. In development, with `EMAIL_MODE=log`, the tell is reversed (a known address answers at once, an unknown one waits): development only, since that mode is refused anywhere else.
  - **The recovery** is a row the server holds, found by the hash of the cookie's key. It names its account only when one may sign in, never discloses it, and stores the address only masked and as a SHA-256 digest. It lives as long as a reset link, an hour.
  - **Another link** is asked for through the recovery, without an email. A recovery may ask 3 times, each at least 60 seconds after the last link, a window the same for every address, so it reveals nothing. The ask is recorded before the account is read, so the position moves the same whether or not an email follows. It counts under the request's own limits ([Rate limits](#rate-limits-fixed-window)), and every email goes through the caps below.
  - **The link** is `<web origin>/reset-password#token=…`. The token rides in the URL fragment, which no server ever receives, so it reaches no hosting log and no `Referer` header. The web reads it there and removes it from the address bar.
  - **The check** (`POST /auth/password/reset/check`) binds the link to the browser's recovery, or opens one for it in a browser that holds none ([why](../features/auth.md#decisions)). It answers with the account's email, masked. It neither uses the token nor extends it, the recovery then lives as long as the link, and a link is bound to one recovery at a time. It answers the same `RESET_TOKEN_INVALID` for an unknown, expired or used link. From the check on, the web holds no credential.
  - **Success** reads the link from the recovery, never from the request: a token in the body is refused (422). It sets the password, ends every session, and every recovery bound to a link of the user, and clears the recovery cookie. The check and the success refuse a link of an account whose temporary password became pending after it was sent. A recovery bound to no link stays, as one for an address with no account does, so the reset tells no one else whether the address has an account.
  - **The token is never logged** outside development. The request logger never logs bodies, and the log mode below is refused anywhere else.
- **The reset email's delivery** is the email port of the `auth` module ([conventions R5](conventions.md#8-module-rules)), in one of two modes, chosen by `EMAIL_MODE`:
  - `log`, the default, sends nothing and writes the message, with its link, to the log. It is allowed in development only;
  - `smtp` sends through an SMTP relay ([the sender](../features/auth.md#decisions)). Its credentials live only in `apps/api/.env`.
  - **Production refuses to start** unless the mode can deliver: `log` is refused there, and `smtp` needs every setting.
  - **The caps**, a decorator over either mode, so development exercises them too: at most 3 emails an hour to one inbox, at most 10 delivered a day asked for from one address (only a delivered email keeps its count), and at most 100 a day in all, which protects Gmail's daily quota and the sender's reputation. They count in the rate-limit table, by digests, so no address is stored. When a cap cannot be checked, nothing is sent. Reaching the daily ceiling writes a `[email:ceiling]` line to the log.
  - **The email** greets no one by name: registration proves no inbox, so the name is anyone's words, and would reach any address through Masaha's genuine sender.
- **Recovery without the email:** the person contacts Masaha on WhatsApp, and the admin issues a temporary password (`mustChangePassword`), after confirming who they are. It replaces the account's password, ends every session and pending reset link, as a reset does, and replaces a temporary password still pending. It is refused for the admin's own account, a suspended account (restored first) and a Google-only one, which has no password to recover: its way in is Google. The action is audited, and its handover recorded after it is shown ([the contract](../api/api-contract.md#users-the-admin)). An owner may also issue one to their own reception staff while one is pending, the admin's recovery included, never to an account that holds anything else ([the contract](../api/api-contract.md#staff-managed)).

## Authorization

The model (roles, space scope, what each role may do) is owned by [ADR 0002](../architecture/decisions/0002-authorization-model.md). Mechanisms:

- `requireAuth` → 401 without a valid token. It then reads the account by the token's id, on every request: 401 for an account that does not exist, for a suspended one, for a token whose session version is not the account's ([Tokens and cookies](#tokens-and-cookies)), and for a token signed before a temporary password ([Passwords](#passwords)) (no code: each ended every session, so the web's refresh is refused and the session ends). The last two checks overlap, since a temporary password raises the version: the pending check stays as a second guard for any future path that sets a temporary password; the role the request carries is the account's now, never the token's ([ADR 0003](../architecture/decisions/0003-session-model.md), revised). Last, for an idle-bound account (reception only, [Tokens and cookies](#tokens-and-cookies)), its session: 401 once signed out, 401 `SESSION_IDLE` once idle past 15 minutes, else renewed unless the route is passive; this reads the account's link roles (one indexed query on every signed-in request but the admin's) and, for reception, the session's last use. 2026-10-25, #118. `requireRole(...roles)` → 403.
- Services call `can(actor, action, resource)`; the space scope and the role at the space (`OWNER` or `RECEPTION`) come from the user's active `SpaceManager` link, never from the global role or the client ([ADR 0009](../architecture/decisions/0009-space-scoped-reception-role.md)).
- **The managed-space boundary**, `requireSpaceAccess`, mounted once on `/manage/spaces/:spaceId`, admits a caller only when `can()` allows them `space.read` there: an active `OWNER` or `RECEPTION` link. Anyone else (no link, a deactivated one, an unknown or a soft-deleted space) gets `not_found` (404), so an unrelated caller cannot learn whether the space exists; a hidden live space stays open to its active links. Each write is then decided by its own `can()` action, owner-only or the staff's, in its service, under the space's lock. The managed photo and package writes, the staff routes, the settings and capacity routes, the live status's override (`space.liveStatus.override`, the staff's), and the desk's writes (`attendance.record`, the staff's, a subscriber's check-in included, 2026-10-22, #109; a visit's payment after its check-out and its debt left to a customer, `payments.record`, the staff's; a visit's write-off and its undo, `visits.writeOff`, the owner's, 2026-10-20, #100; a payment's void, `payments.void`, the owner's, 2026-10-24, #114), a customer's creation and edit (`customers.manage`, the staff's), a customer's archive and restore (`customers.archive`, the owner's, 2026-10-21, #102), subscribing a customer, correcting a subscription's limits, dates and name, and ending it early (`subscriptions.manage`, the staff's), and correcting its price or billing (`subscriptions.correctPrice`, the owner's, 2026-10-22, #106), and an announcement's post, edit, end, start and delete (`announcements.manage`, the staff's, 2026-10-24, #112), ask `can()` first, at the route, through `requireCan(action)`: a caller who may not change them is refused (403) before the request is counted or its body read; the service still decides under the lock.
- **A price typed by hand at the desk** is decided by `can()`'s `prices.typeByHand`, from the space's switch read with its settings: the owner always, reception only where the space allows it, else `forbidden` (403) `PRICE_TYPING_NOT_ALLOWED` ([data-model › Front desk and money](../architecture/data-model.md#front-desk-and-money)). 2026-10-20, #95. Pricing an unpriced visit later is decided the same way, after `requireCan('attendance.record')` at its route and the staff's `can()` under the space's lock. 2026-10-20, #97.
- **The payments list** is the staff's read, narrowed in its service by `can()`'s `payments.read` before any query: the owner reads every payment of the space; reception its own of today (Gaza): the query is validated first (422), and a valid range or `recordedById` from reception is then `forbidden` (403), never ignored. 2026-10-24, #114.
- Suspended users cannot log in or refresh, and their unexpired access tokens are refused.
- **The admin edits a space's facts only while it is unverified,** with no active `OWNER` link; once an owner has joined, the owner does. Resolving its data reports follows the same rule: on `/admin/data-reports`, `can()` reads the space's links under its lock, so an owner linked while the admin's decision waits makes it `forbidden` (2026-10-25, #120). `can()` decides, from the links on the request ([conventions › Space access](conventions.md#space-access)).
- **A space's data reports are its owner's** (`space.dataReports.read` to list them, `dataReports.resolve` to decide one): `requireCan` refuses reception before the query or the body is read, and the decision asks `can()` again on the links read under the space's lock, so an owner unlinked meanwhile is refused. The owner never sees who reported: the list's query selects no reporter. 2026-10-25, #120.
- **A space's audit log is its owner's** (`space.auditLog.read`): `requireCan` refuses reception before the query is read; the admin, who has no link to a space, is refused by the boundary like any stranger. In the log, the admin is `MASAHA`, never named (2026-10-27, #128).
- **The admin's audit log is the platform's events only** (`/admin/audit-log`, behind `/admin`'s guard): a default-deny list ([conventions §6](conventions.md#6-audit)) — never an entry about a space's customers, subscriptions, check-ins, visits, payments, packages, announcements or extensions, its capacity, its override, its settings or its staff (2026-10-27, #128).
- **A space's finance is its owner's** (`finance.read`): each route under `/manage/spaces/:spaceId/finance` asks `requireCan` before the query is read, so reception is refused (403); the admin, who has no link to a space, is refused by the boundary like any stranger. 2026-10-29, #131.
- **The owner's overview is the owner's** (`space.overview.read`): `requireCan` refuses reception, which has none; the admin, who has no link to a space, is refused by the boundary like any stranger. It holds no amount (2026-10-29, #131).
- **The admin's overview is the platform's figures only** (`/admin/overview`, behind `/admin`'s guard): never a space's customers, visits, subscriptions, payments, capacity or presence; no `can()` action of its own, as every admin route (2026-10-29, #131).
- **A closure's extension is its owner's** (`subscriptions.extendAfterClosure`): `requireCan` refuses reception before the key or the body is read, and the extension asks `can()` again on the links read under the space's lock, so an owner unlinked meanwhile is refused. Its preview is the staff's. 2026-10-26, #123.
- **A suspension keeps the account's links:** a suspended owner's space stays verified, so while the owner is suspended the admin edits it only after unlinking them.

## Rate limits (fixed window)

The counters are stored in PostgreSQL, in the `rate_limits` table, so every instance of the API shares them: online, the API runs as functions that share no memory ([ADR 0014](../architecture/decisions/0014-deployment.md)).

**What each limit counts by.** Masaha's users sit in coworking spaces, where everyone shares one network address. A limit keyed only by the address would lock a whole space out, so each limit counts by what it protects:

| Scope | Counts | Limit |
|---|---|---|
| Password sign-in and register | **Failed** attempts only, by address and email: brute force against one account | 10 / 15 min |
| | **Failed** attempts only, by address: one address trying many accounts | 50 / 15 min |
| Register | **Every** registration, by address, counted before the password is hashed: each costs a bcrypt hash and an account row | 20 / hour |
| Google sign-in | **Failed** attempts only, by address, under its own key: junk tokens fail in microseconds, so they lock only Google sign-in out, never the password sign-ins of a shared address | 50 / 15 min |
| Refresh | Every refresh, by the user its cookie belongs to. The token is random and cannot be guessed, so an unknown cookie is simply refused | 30 / 15 min |
| Password forgot | Every request for a link, and every resend, by address and email (a digest of it, which the recovery keeps), beside the reset email's own caps ([Passwords](#passwords)) | 5 / 15 min |
| Password reset and its check | Every request, by address and token (the check) or by address and recovery (the reset) | 5 / 15 min |
| Password forgot, resend, reset and check together | Every request, by address | 50 / 15 min |
| Data reports | Every report, by the user, counted at the route before the body is read: a repeat of an open one and an invalid body included | 10 / hour |
| Photo uploads | Every upload, by the user, counted before the file is read: each costs a decode and the store's free allowance | 30 / 15 min |
| Staff accounts | Every creation and re-issue by an owner, by the owner, counted before the body is read: each costs a bcrypt hash | 10 / hour |
| Password change | **Failed** attempts only (a wrong current password), by the user: a thief can change address | 10 / 15 min |
| General API, signed in | Every request, by the user | 300 / 15 min |
| General API, guest | Every request, by address: live-status polling from one space's shared address | 1,200 / 15 min |

**The mechanism** is `shared/rate-limit`, a small limiter over the counter:
- Every count is one atomic statement on its key, and every count is written **before the response is sent** (ADR 0014).
- A limit on failures reserves each attempt, atomically, before it runs, and returns the slot on a success or a server failure (a 5xx), before answering: a refused attempt keeps its slot as the failure. A concurrent burst therefore cannot pass the limit, and while a slot is held a burst larger than the limit is refused beyond it, even when its passwords are right. A refused attempt (429) keeps its count: so after such a burst, or after enough failures, even the correct password is refused until the window ends.
- A key is the policy's name and a SHA-256 digest of what it counts by, so the table holds no address, email or token in clear. The digest is not anonymous: an IPv4 address, or a known email, is found again by hashing the candidates.
- The address is `req.ip`, which depends on `TRUST_PROXY` (the proxies Express trusts). An IPv6 address counts by its /64 network.
- A 429 carries the error envelope, `Retry-After` and the `RateLimit-Policy` and `RateLimit` header fields.
- `express-rate-limit`, approved in the foundation plan, is **not used**. It counts failures-only limits by adding every request and subtracting the successes after the response is sent: work after the response, which ADR 0014 forbids.

## Location

Near me ([directory](../features/directory.md)) sorts on the server, so the device's location reaches the API (the owner's change, 2026-10-13: it was never sent). These rules keep it from going further:

- **It is sent in a header, only to sort by distance:** the directory's list, and a user's favourites (`GET /me/favorites`, #121). The `Masaha-Near: lat,lng` request header, never the query: a URL is written by the hosting's own request log and by any proxy's, which Masaha cannot redact; a header is not. The API refuses the header with any other order, and refuses distance without it ([the contract](../api/api-contract.md#directory-public)).
- **It is rounded on the device, to 3 decimals** (about 110 m by 95 m in Gaza): a block of many buildings, not a home, yet fine enough for "near" among spaces that sit close together. The API **refuses a finer point** (`invalid_format`), so a client that skips the rounding fails rather than sending a precise location.
- **It is never stored or logged.** It is read with the query and kept off the request, passed to the database only as a query parameter, and never written; the request logger redacts the header ([HTTP hardening](#http-hardening)). An API test reads the whole log line of a request that carries it.
- **No cache keeps an answer to a request that carries it:** every such answer, a refusal or a failure included, is `Cache-Control: no-store`; on the favourites it is set before the sign-in guard, so the guard's refusal too (#121). Each distance in it is a bare number, straight-line, from the rounded point, to the nearest 100 m; the screen labels it approximate.

## HTTP hardening

- `helmet` defaults; CORS allows one origin from the environment with credentials; `trust proxy` set.
- JSON body limit 16 kB.
- **Photos:** one file per request, at most 4 MiB, so the request stays under the platform's 4.5 MB limit with its multipart framing ([ADR 0014](../architecture/decisions/0014-deployment.md)); the web shrinks a photo before sending it. Online, a larger request is refused by the platform itself, before the API (a 413 without the envelope).
  - **Decoding is the content check:** sharp decodes the file, and anything it cannot decode as a JPEG, a PNG or a WebP is refused (415); the file's name and declared type are never read. An image over 50 megapixels is refused before it is decoded (413), so a small file that would expand to gigabytes costs nothing.
  - **Re-encoded, with nothing but its pixels:** each photo is turned the way its EXIF says, then encoded again as WebP sizes with no metadata: no EXIF (so no GPS position or camera), no XMP, no ICC profile. The original is never stored.
  - **Stored under a random key** (128 bits), which names nothing about the uploader; the store receives only the WebP files.
- The server refuses to start without a reachable database; graceful shutdown on SIGTERM/SIGINT.
- **`JOBS_SECRET` is a secret:** the timed jobs' endpoint ([api-contract › Internal](../api/api-contract.md#internal)) is mounted only when it is set, and production requires it. At least 32 characters; compared in constant time, through the SHA-256 digests of the header and of `Bearer <JOBS_SECRET>`; never logged (the request logger redacts the `authorization` header). 2026-10-20, #97.
- **`CLOUDINARY_URL` is a secret:** it holds the storage account's API secret. It lives only in `apps/api/.env` (and the host's settings online), is never logged, and a malformed one is refused at startup without echoing it. Requests to Cloudinary are signed with it, and it is never sent.
- **The HTTP logger redacts** the `cookie`, `authorization`, `masaha-near` ([Location](#location)) and `set-cookie` headers, and any field named like a password or a token, and **never logs request bodies**. It is built in `shared/http`. The other logging rules are in [backend conventions §10](conventions.md#10-logging).
